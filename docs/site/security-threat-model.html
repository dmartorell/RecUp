Seguridad

Threat model y tradeoffs

Tabla de amenazas identificadas, cómo están mitigadas y qué riesgos se han aceptado conscientemente. El objetivo no es seguridad perfecta, sino que los riesgos residuales sean conocidos y proporcionados al contexto (herramienta interna, dominio restringido).

Resumen de amenazas

Login enumeration — Mitigado

Si un usuario no existe, el servidor igualmente ejecuta un bcrypt.compare contra un hash fijo (DUMMY_HASH) para igualar el tiempo de respuesta al caso de contraseña incorrecta. Sin esto, la diferencia de latencia (~100 ms de bcrypt vs. respuesta inmediata) permitiría enumerar qué emails están registrados. 

// server/routes/auth.js:14
const DUMMY_HASH = bcrypt.hashSync('dummy-password-for-timing-mitigation', 12);

// ...cuando el usuario no existe:
await bcrypt.compare(password, DUMMY_HASH);
return res.status(401).json({ error: 'INVALID_CREDENTIALS' });

Register enumeration — Aceptado

POST /api/auth/register devuelve 409 EMAIL_TAKEN cuando el email ya existe. Esto filtra qué emails están registrados.

Por qué se acepta:

  • El registro está restringido a un dominio corporativo (ALLOWED_EMAIL_DOMAIN). El atacante ya conoce el dominio.
  • Sin infraestructura de email transaccional no hay forma de notificar al titular legítimo de un intento de registro duplicado.
  • La alternativa (devolver 201 siempre + notificar por email) requiere email infra que hoy no existe.
Revisitar cuando exista email transaccional

Cambiar a respuesta genérica 201 + enviar notificación al titular cuando se añada capacidad de envío de emails.

Brute force login — Mitigado

Las rutas /api/auth/login y /api/auth/register tienen un rate limiter en memoria: máximo 10 peticiones por IP en ventanas de 60 segundos. Superar el límite devuelve 429 RATE_LIMITED. 

// server/middleware/rateLimiter.js
const recent = (attempts.get(key) || []).filter((t) => now - t < windowMs);
if (recent.length >= max) {
  return res.status(429).json({ success: false, error: 'RATE_LIMITED' });
}
Limitación multi-instancia

El state es in-memory por proceso. Con varias instancias de Render (horizontal scaling), cada instancia tiene su propio contador: un atacante que distribuya peticiones entre instancias evita el límite. Solución: Redis compartido. Ver Escalabilidad.

Volcado de BD — Mitigado

Si Turso es comprometido, el atacante obtiene:

  • API keys — ciphertext enc:v1:… inutilizable sin CRYPTO_SECRET.
  • Contraseñas — hash bcrypt (coste 12), resistente a fuerza bruta.
  • Emails, nombres, transcripciones — en claro. Riesgo residual conocido.

Detalle completo del esquema de cifrado en Cifrado de API keys en reposo.

RCE en Render — No mitigado

Si un atacante consigue ejecutar código en el proceso de Node.js (p.ej. a través de una dependencia comprometida), puede leer las variables de entorno del proceso: CRYPTO_SECRET, JWT_SECRET, TURSO_AUTH_TOKEN, etc. Con eso puede descifrar todas las API keys de la BD.

Mitigaciones robustas requerirían:

  • KMS (AWS KMS, Google Cloud KMS) — la clave de cifrado nunca está en memoria, solo se piden operaciones criptográficas al KMS.
  • HSM o enclaves seguros.

Ambas opciones son desproporcionadas para el contexto actual (herramienta interna, equipo pequeño). El riesgo se acepta. Si el scope crece, revisar.

JWT robado — Parcial

El JWT se guarda en localStorage. Un script XSS puede leerlo. No es posible usar httpOnly porque la SPA necesita adjuntarlo manualmente a cada fetch (no hay cookie automática).

Las capas de contención actuales:

  • TTL de 7 días: la ventana de explotación de un JWT filtrado está acotada.
  • Logout global por 401: si el servidor detecta un JWT inválido o expirado, el cliente limpia sesión y redirige al login. Ver JWT y autenticación.
  • Reducir la superficie XSS limita la probabilidad de que el JWT sea accesible.

XSS en la SPA — Parcial

La SPA es vanilla JS. Los paths de riesgo son los puntos donde se inserta contenido externo en el DOM.

  • Paths seguros: la mayoría de campos de incidentes se insertan vía textContent o atributos data-*, que no interpretan HTML.
  • Paths a revisar: cualquier uso de innerHTML con datos que procedan de transcripciones o del backend (contenido generado por el usuario o por la IA). Aunque la IA devuelve JSON estructurado, una inyección en el prompt podría producir HTML en los bullets.
Regla práctica

Usar siempre textContent para contenido de usuario. Reservar innerHTML exclusivamente para HTML estático controlado por el desarrollador.

Fuera de scope (decisión explícita)

  • CSRF — la SPA no usa cookies de sesión; el JWT va en Authorization: Bearer, que CSRF no puede falsificar desde otro origen.
  • Clickjacking — herramienta interna; el riesgo es mínimo. Añadir X-Frame-Options: DENY si se expone públicamente.
  • Dependency audit — no hay pipeline automático de bun audit. Riesgo bajo-medio aceptado para el volumen actual.
