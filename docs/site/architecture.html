Visión general

Arquitectura general

RecUp conecta cuatro capas: un cliente web (SPA vanilla JS) y una extensión de Chrome que actúan de entrada, un backend Express desplegado en Render que orquesta toda la lógica, una base de datos Turso (libSQL/SQLite) como persistencia, y tres APIs externas (Anthropic, OpenAI y ClickUp).

Flujo principal

El happy path de un bug report completo, de punta a punta:

  1. El usuario graba audio o escribe texto en la SPA.
  2. La SPA envía POST /api/incidents al backend → se guarda el incidente con status: procesando.
  3. La SPA envía POST /api/summarize. El backend lee el ai_provider del usuario, descifra su API key y llama a Anthropic u OpenAI. Devuelve JSON estructurado (título + bullets + transcripción).
  4. La SPA persiste el resultado con PATCH /api/incidents/:id y renderiza el card.
  5. Si la IA detecta que es un bug, el modal de ticket se abre automáticamente. El usuario puede completarlo y enviar POST /api/ticket. El backend resuelve el email del reporter a un userId de ClickUp (caché 10 min) y crea la tarea con adjuntos.

Entrada desde la extensión

La extensión no tiene backend propio. Al hacer clic en "Enviar a RecUp", abre la webapp con query params: ?token=<jwt>&email=<e>&name=<n>&contextText=<texto>.

La SPA detecta estos params en app.js → adoptExtensionSession(), inicia sesión directamente y pre-carga el texto. Después, history.replaceState limpia la URL para que el token no quede expuesto en el historial del navegador.

Sin login extra

El JWT que emite el servidor al hacer login desde la extensión es idéntico al de la SPA. No hay sesiones separadas ni handshake especial: la extensión simplemente reusa el token existente.

Decisiones de diseño relevantes

  • Sin bundler. La SPA se sirve como archivos estáticos desde Express (server/index.js). Sin Webpack, Vite ni build step: más simple, más fácil de depurar, suficiente para el tamaño actual.
  • API keys cifradas en BD. Las claves de Anthropic, OpenAI y ClickUp de cada usuario se guardan cifradas con AES-256-GCM. El servidor las descifra on-demand. Si alguien vuelca la BD, las keys no sirven de nada sin CRYPTO_SECRET. → Cifrado de API keys
  • Rate limiter in-memory. Sencillo y suficiente para una instancia. En multi-instancia rompe. → Límites actuales
  • IA configurable por usuario. Cada usuario debe configurar su propia API key de Anthropic u OpenAI. Sin key, POST /api/summarize devuelve 400 SETTINGS_NOT_CONFIGURED. No hay fallback del servidor.

Testing

Tests con bun:test y SQLite :memory: vía tests/preload.js. No hay mocks de base de datos: los tests lanzan el servidor real contra una BD efímera. 

bun test                    # todos
bun test tests/auth.test.js # un archivo
bun test --test-name-pattern "POST /api/auth"
