Operación

Despliegue en Render + secrets

RecUp corre en Render como un Web Service. Esta página es el runbook: dónde vive cada variable de entorno, qué pasa si rotas un secreto y cómo levantar el entorno local sin tocar la base de datos de producción.

Comando de arranque

Render ejecuta el comando configurado en el dashboard del servicio. El equivalente local es: 

node --import ./server/instrument.js server/index.js

El flag --import carga server/instrument.js antes que cualquier otro módulo, lo que garantiza que el SDK de Sentry está inicializado antes de que Express procese cualquier request. En desarrollo con hot-reload: 

bun --watch server/index.js
bun --watch no carga instrument.js

En desarrollo con bun --watch, Sentry no se inicializa (no hay --import). Es intencional: en local no interesa enviar errores a Sentry. Si SENTRY_DSN no está configurada, el SDK simplemente no se activa (server/instrument.js:6).

Variables de entorno

Se configuran en el dashboard de Render: Service → Environment → Environment Variables. No están en el repositorio.

Variable ¿Obligatoria? Notas
TURSO_DATABASE_URL Sí URL de Turso: libsql://<db>-<org>.turso.io. En local con :memory: para tests.
TURSO_AUTH_TOKEN Sí en prod Token de Turso. Omitir en local con :memory: (no se autentica).
JWT_SECRET Sí Clave HMAC para firmar JWTs. El servidor no arranca si falta. Rotar invalida todos los tokens emitidos.
CRYPTO_SECRET Sí Clave para AES-256-GCM. El servidor no arranca si falta. Perder este valor hace irrecuperables todas las API keys cifradas en BD.
CLICKUP_API_KEY No API key de ClickUp a nivel de servidor. Se usa en registro para verificar que el email pertenece al workspace. Si falta, el registro es fail-open.
ALLOWED_EMAIL_DOMAIN No Si está presente (p. ej. @alfredsmart.com), solo se permiten registros con ese dominio.
SENTRY_DSN No DSN de Sentry. Si no está, el SDK no se activa y no se envían errores.
SENTRY_ENVIRONMENT No Tag de entorno en Sentry. Por defecto: development. Poner production en Render.
PORT No Puerto en el que escucha Express. Por defecto: 3000. Render lo inyecta automáticamente.

Checklist de secretos críticos

Antes de un primer despliegue o tras un reset, verificar que estas variables están configuradas en Render:

  • JWT_SECRET — generar con openssl rand -base64 48. Largo y aleatorio.
  • CRYPTO_SECRET — generar con openssl rand -base64 32. Guardar una copia offline en lugar seguro. Si se pierde, las API keys de todos los usuarios son irrecuperables.
  • TURSO_DATABASE_URL y TURSO_AUTH_TOKEN — obtener del dashboard de Turso (Database → Connect).
Nunca commitear estos valores

El fichero .env.example tiene las claves en blanco a modo de plantilla. El .gitignore excluye .env. Si accidentalmente se hace commit de un secreto real, rotarlo inmediatamente (Render → Environment → editar variable) y considerar el antiguo comprometido.

Rotar JWT_SECRET

Cambiar JWT_SECRET en Render y redesplegar invalida todos los JWTs emitidos. Los usuarios activos recibirán un 401 en su próxima request autenticada, lo que dispara el logout automático y los redirige al login.

  1. Generar el nuevo secret: openssl rand -base64 48.
  2. Actualizar la variable en Render → Manual Deploy (o esperar el siguiente deploy automático).
  3. Avisar al equipo: todos tendrán que volver a hacer login.

No hay sesiones persistidas en BD (el JWT es stateless), así que no hace falta migrar nada.

Rotar CRYPTO_SECRET

Más delicado que rotar el JWT: las API keys cifradas en BD son irrecuperables con el secret antiguo una vez cambiado. El proceso seguro:

  1. Con el servidor corriendo y el secret antiguo activo, exportar todas las API keys descifradas (script ad-hoc contra Turso).
  2. Generar el nuevo secret: openssl rand -base64 32.
  3. Re-cifrar todas las keys con el nuevo secret y actualizar las filas en Turso.
  4. Actualizar CRYPTO_SECRET en Render y redesplegar.

Actualmente no existe este script. Si se compromete el secret y no hay tiempo para la rotación ordenada, la opción rápida es poner todas las columnas de API key a NULL en Turso y pedir a los usuarios que las reconfiguren.

Ver más detalle en Cifrado de API keys → Rotación.

Desarrollo local

Con SQLite en memoria (sin Turso)

Para desarrollo y tests, el servidor acepta una BD SQLite en memoria. No necesita TURSO_AUTH_TOKEN ni conexión de red: 

# .env local (no commitear)
TURSO_DATABASE_URL=:memory:
JWT_SECRET=dev-secret-local
CRYPTO_SECRET=dev-crypto-local-32bytes-padding!
bun --watch server/index.js

La BD se inicializa vacía en cada arranque. Usar bun scripts/seed-users.js para crear usuarios de prueba.

Con Turso local o remoto

Para probar con datos reales de desarrollo (no la BD de prod), crear una BD separada en Turso (Create database) y apuntar TURSO_DATABASE_URL a ella. Nunca apuntar el entorno local a la BD de producción.

Tests

Los tests usan siempre :memory: via el preload tests/preload.js, que sobreescribe TURSO_DATABASE_URL antes de que cargue cualquier módulo. No requieren configuración adicional: 

bun test

Archivos clave

  • server/config/env.js — validación de variables al arrancar; las obligatorias llaman a process.exit(1) si faltan
  • server/instrument.js — inicialización de Sentry, cargado antes que todo lo demás vía --import
  • .env.example — plantilla de variables (sin valores reales)
  • tests/preload.js — sobreescribe TURSO_DATABASE_URL=:memory: para tests
  • scripts/seed-users.js — crea usuarios de prueba en la BD local
