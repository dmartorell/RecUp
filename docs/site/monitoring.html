Observabilidad · Errores

Sentry

RecUp usa Sentry como único sistema de monitorización de errores en producción. Está activo en el backend (Express) y en la app web (SPA). La extensión de Chrome no envía a Sentry. La configuración es mínima a propósito: solo errores, sin tracing, sin PII por defecto.

Alcance y filosofía

  • Solo errores. tracesSampleRate: 0 en ambos extremos: no se mandan transacciones de performance ni spans. Lo único que llega a Sentry son excepciones y errores no capturados.
  • PII off por defecto. sendDefaultPii: false evita que Sentry adjunte IPs, cookies o headers automáticamente. El único dato personal que se envía es el email del usuario y de forma explícita (ver Identificación de usuario).
  • Cobertura ≠ telemetría. Sentry es para detectar regresiones y errores en prod, no un APM. Logs de aplicación siguen en stdout (Render); analytics no hay.
  • Extensión fuera. La extensión vive en el contexto del navegador del usuario sobre páginas de terceros — Sentry generaría más ruido que señal (ver denyUrls).

Backend (Express + Node/Bun)

Inicialización

El SDK @sentry/node se inicializa en server/instrument.js, un fichero sin imports de la app: 

import 'dotenv/config';
import * as Sentry from '@sentry/node';

const dsn = process.env.SENTRY_DSN;

if (dsn) {
  Sentry.init({
    dsn,
    environment: process.env.SENTRY_ENVIRONMENT || 'development',
    tracesSampleRate: 0,
    sendDefaultPii: false,
  });
}

export { Sentry };
Por qué se carga antes que cualquier otro módulo

Sentry instrumenta automáticamente http, express, etc. para capturar errores. Para hacerlo necesita parchear esos módulos antes de que el resto del código los importe. Por eso instrument.js se inyecta vía el flag de arranque, no como un import normal: 

"start": "node --import ./server/instrument.js server/index.js",
"dev":   "bun --preload ./server/instrument.js --watch server/index.js"

Si lo importases desde app.js, Express ya estaría cargado sin instrumentar y se perderían capturas.

Orden de los error handlers

En server/app.js, el handler de Sentry se registra antes del handler propio: 

// …rutas…
Sentry.setupExpressErrorHandler(app);   // captura y envía a Sentry
app.use(errorHandler);                  // formatea respuesta JSON al cliente

El orden es importante:

  1. Una ruta llama a next(err).
  2. Express busca el siguiente middleware de error. Encuentra el de Sentry primero, que captura la excepción y la pasa al siguiente.
  3. Llega a errorHandler, que serializa el error como { success: false, error: 'INTERNAL_ERROR' } y responde 500 (o el status que toque).

Si invirtieras el orden, errorHandler respondería primero y Sentry nunca vería el error.

Degradación sin DSN

Si SENTRY_DSN no está definido, Sentry.init nunca se llama. El SDK queda en estado no-op: setupExpressErrorHandler existe y no falla, pero no envía nada. Esto permite:

  • Levantar local sin tocar nada — basta no setear la env var.
  • Correr tests sin generar tráfico ni ruido en Sentry.
  • Apagar Sentry en una emergencia borrando la env var y reiniciando.

App web (SPA)

Inicialización

El SDK del navegador se carga vía CDN en el <head> de src/index.html, pinneado a una versión concreta y con SRI: 

<script
  src="https://browser.sentry-cdn.com/10.55.0/bundle.min.js"
  integrity="sha384-bxrw1+kSICicOnYIsIuCMwwSPMLE5565At6u56u5+WgEjG9NQWsS01Q0pZTHwoeL"
  crossorigin="anonymous"
></script>
Para qué sirve el integrity="sha384-…"

Es Subresource Integrity (SRI). El navegador descarga el JS, calcula su SHA-384 y lo compara con el hash declarado. Si no cuadra, no lo ejecuta. Esto blinda contra:

  • Compromiso del CDN sirviendo un bundle alterado.
  • MITM en redes inseguras inyectando código en el SDK.

Coste: cada bump de versión del SDK requiere regenerar el hash. El comentario sobre el <script> ya deja el comando preparado: 

curl -sSL "<URL>" | openssl dgst -sha384 -binary | openssl base64 -A

Configuración

Sentry.init({
  dsn: 'https://b8a22…@o45…ingest.de.sentry.io/45…',
  environment: isProd ? 'production' : 'development',
  sampleRate: 1.0,
  tracesSampleRate: 0,
  sendDefaultPii: false,
  ignoreErrors: [
    'ResizeObserver loop limit exceeded',
    'ResizeObserver loop completed with undelivered notifications',
    'Non-Error promise rejection captured',
    'Network request failed',
  ],
  denyUrls: [
    /^chrome:\/\//i,
    /^chrome-extension:\/\//i,
    /^moz-extension:\/\//i,
    /^safari-extension:\/\//i,
    /extensions\//i,
  ],
});

Cosas a destacar:

  • DSN hardcodeado, no en env. La SPA es estática, no hay backend de build, y el DSN de browser está diseñado para ser público — solo permite ingestar, no leer. Meterlo en variables de entorno no aporta nada salvo complejidad.
  • Detección de entorno por hostname: isProd = hostname !== 'localhost' && !hostname.startsWith('127.'). Sin variables ni build steps.
  • sampleRate: 1.0: se envían el 100% de los errores. El volumen es bajo, no compensa hacer sampling.

Reducción de ruido: ignoreErrors

Cuatro patrones de ruido típico de navegador, no son bugs de la app:

  • ResizeObserver loop …: warning espurio de Chrome que aparece cuando un observer reagenda layout. No es un error real, no afecta UX.
  • Non-Error promise rejection captured: típicamente código de terceros que rechaza promises con un string o un objeto vano. Sin stack útil.
  • Network request failed: el usuario perdió conectividad o navegó mientras una request estaba en vuelo. Sentry no debe paginar a nadie por esto.

Reducción de ruido: denyUrls

Esto es lo que aísla la SPA de los errores que no son nuestros: 

denyUrls: [
  /^chrome:\/\//i,
  /^chrome-extension:\/\//i,
  /^moz-extension:\/\//i,
  /^safari-extension:\/\//i,
  /extensions\//i,
],

Cuando Sentry captura un error, mira la URL del frame superior del stack. Si coincide con cualquiera de estas regex, descarta el evento. Filtramos:

  • Páginas internas del navegador (chrome://).
  • Extensiones del usuario (Grammarly, traductores, password managers, etc.) que parchean el DOM e introducen errores en su propio código.

Sin esto, los issues de Sentry se llenan de errores de extensiones aleatorias que ni reproducimos ni controlamos. Es la regla de filtrado más rentable que tiene la SPA.

Identificación de usuario

La única PII que viaja a Sentry es el email del usuario logado, adjuntada como contexto del evento mediante Sentry.setUser(). No se envía nombre, avatar, ni IPs (las suprime sendDefaultPii: false).

Dónde se llama

El helper vive en src/js/auth.js y se re-aplica en cada punto donde la sesión cambia: 

export function tagSentryUser() {
  if (!window.Sentry) return;
  const email = getSession()?.user?.email;
  window.Sentry.setUser(email ? { email } : null);
}
  • Boot de la SPA (inline en index.html): si ya hay recup_session en localStorage, se tagea el usuario antes incluso de cargar la app.
  • Login: tras un login exitoso se llama tagSentryUser().
  • Handoff de la extensión: cuando la SPA adopta la sesión que viene de la extensión (URL params o postMessage), se vuelve a tagear.
  • Refresh de /api/auth/me: al recuperar el perfil.
  • Logout: setUser(null) implícito vía la rama email ? … : null.
Nunca añadir más PII

Tenemos un dominio corporativo controlado (ALLOWED_EMAIL_DOMAIN) y por eso el email se considera asumible. Cualquier otro campo que se pase a setUser o como contexto pasa por revisión: nombre real, id, IP, etc., obligan a un análisis previo. El default es no enviar.

Entornos

En Sentry los issues se filtran por environment, así que el dashboard de prod no se contamina con eventos de dev/local.

Probar la integración

  • Backend: lanza una ruta que tire throw new Error('test') y comprueba en Sentry que aparece con el environment esperado.
  • SPA: en la consola del navegador throw new Error('test sentry') o Sentry.captureMessage('hola', 'info').
  • Para no enviar mientras pruebas, basta con quitar el DSN del backend o cargar la SPA desde localhost (cae en environment development y los issues se filtran en el dashboard).

Trade-offs conscientes

  • Sin tracing. Si en algún momento aparecen problemas de performance reales, activar tracesSampleRate a un valor pequeño (0.05–0.1) y volver a evaluar.
  • Sin Session Replay. Sería útil para reproducir bugs UI, pero implica más PII (DOM + inputs). Por ahora compensa la simplicidad.
  • Sin source maps subidos. Los stacks de la SPA son contra el bundle.min.js de Sentry, pero el código propio es ESM sin minify y los stacks son legibles. Cuando entre un build step de minificación habrá que subir source maps a Sentry.
