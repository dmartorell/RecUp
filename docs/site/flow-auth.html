Login y registro

Cómo un usuario entra en RecUp: validación de dominio, comprobación bcrypt, emisión del JWT y su almacenamiento en cliente. También cubre la renovación silenciosa del token y el logout global ante un 401.

Visión general

[Frontend: login form]
        │  POST /api/auth/login  { email, password }
        ▼
[server/routes/auth.js]
  ├── Rate limiter (10 req/min/IP)
  ├── Busca usuario en Turso por email
  ├── bcrypt.compare(password, hash)      ← dummy compare si no existe
  └── signToken(userId, name, email)      ← JWT firmado, TTL 7d
        │
        ▼
{ token, user: { name, email, avatar } }
        │
[Frontend: localStorage.setItem('recup_session', …)]
        └── showApp() → carga incidentes

Registro

El endpoint es POST /api/auth/register (server/routes/auth.js:16). Valida en orden:

  1. Campos obligatorios — name (1–100 chars), email válido, password ≥ 8 chars.
  2. Dominio restringido — si ALLOWED_EMAIL_DOMAIN está configurado, el email debe terminar en ese dominio. Devuelve 400 EMAIL_DOMAIN si no.
  3. Comprobación de workspace ClickUp — si existe CLICKUP_API_KEY a nivel de servidor, verifica que el email pertenece al workspace. Si la llamada a ClickUp falla, el registro continúa (fail-open).
  4. Email único — INSERT INTO users; si hay conflicto UNIQUE, devuelve 409 EMAIL_TAKEN.
  5. Emisión del JWT — en el mismo response del registro, el usuario queda autenticado directamente (no hay paso de login separado).
Tradeoff: enumeración en registro

El 409 EMAIL_TAKEN revela qué emails están registrados. Aceptado porque el dominio ya es conocido. Ver detalle en Threat model.

Login

El endpoint es POST /api/auth/login (server/routes/auth.js:76).

  1. Rate limiter — mismo middleware que en registro.
  2. Busca el usuario en Turso por email.toLowerCase().
  3. Si no existe: ejecuta bcrypt.compare(password, DUMMY_HASH) para igualar el tiempo de respuesta y devuelve 401 INVALID_CREDENTIALS. Sin este dummy compare, la respuesta inmediata revelaría que el email no está registrado.
  4. Si existe: bcrypt.compare(password, user.password). Si no coincide, 401 INVALID_CREDENTIALS.
  5. Resolución del avatar: descifra clickup_api_key del usuario y llama a ClickUp para obtener la URL del avatar. Si lo obtiene, lo persiste en users.avatar_url.
  6. Emite el JWT y devuelve { token, user }.

JWT emitido

La función signToken (server/middleware/auth.js:5) firma un JWT HS256 con:

  • sub — userId (integer)
  • name — nombre del usuario
  • email — email
  • exp — now + 7d (constante JWT_EXPIRES_IN = '7d')

El secret es JWT_SECRET (env var en Render). Si no está configurado, el fallback es 'dev-secret-change-me', que no es seguro en producción.

Almacenamiento en cliente

Tras un login o registro exitoso, el frontend guarda la sesión en localStorage: 

// src/js/app.js:207
localStorage.setItem(
  'recup_session',
  JSON.stringify({ token: data.data.token, user: data.data.user })
);

La clave recup_session contiene token y user: { name, email, avatar }. Al cargar la app, checkAuth() lee esta entrada: si tiene token y user, muestra la app directamente sin un nuevo login.

Por qué localStorage y no httpOnly cookie

La SPA adjunta el JWT manualmente como Authorization: Bearer … en cada fetch. Las cookies httpOnly protejen de XSS pero requieren que el servidor gestione la cookie; ese modelo es más complejo con una SPA pura sin framework de sesión. Ver Threat model — JWT robado.

Renovación silenciosa del token

El authMiddleware (server/middleware/auth.js:21) comprueba en cada request autenticada si el token expira en menos de 3 días (JWT_RENEW_THRESHOLD_MS = 3 * 24 * 60 * 60 * 1000). Si es así, firma un token nuevo y lo devuelve en la cabecera de respuesta: 

res.setHeader('X-New-Token', fresh);
res.setHeader('Access-Control-Expose-Headers', 'X-New-Token');

El frontend tiene un interceptor de fetch instalado al arrancar (src/js/auth.js:57 — installTokenRefreshInterceptor) que detecta esta cabecera y actualiza localStorage transparentemente: 

const fresh = res.headers.get('X-New-Token');
if (fresh) updateSessionToken(fresh);

El usuario nunca ve un prompt de re-login mientras use la app al menos una vez cada 4 días.

Logout global ante 401

Si cualquier fetch autenticado recibe un 401, el interceptor llama a handleExpiredSession() (src/js/auth.js:26), que:

  1. Comprueba el flag window.__recupSessionExpired para ejecutarse solo una vez aunque haya múltiples requests en vuelo.
  2. Elimina recup_session de localStorage.
  3. Emite window.postMessage({ type: 'recup:logout' }) (por si la extensión Chrome escucha).
  4. Muestra un toast de sesión expirada.
  5. Recarga la página tras 1,5 s, lo que lleva al login.

Las rutas públicas (/api/auth/login, /api/auth/register) están excluidas de este comportamiento: un 401 en login es una contraseña incorrecta, no una sesión caducada.

Rutas públicas vs. protegidas

El authMiddleware se aplica explícitamente en cada router que lo necesita. Las únicas rutas que no lo requieren son las de auth. En el servidor, la constante AUTH_PUBLIC_PATHS se replica en el cliente (src/js/auth.js:45) para que el interceptor sepa qué respuestas 401 ignorar. 

const AUTH_PUBLIC_PATHS = ['/api/auth/login', '/api/auth/register'];
