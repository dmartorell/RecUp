Backend · Persistencia

Base de datos

RecUp persiste todo su estado en Turso (libSQL, fork de SQLite con replicación distribuida). El esquema vive en server/db.js y se aplica de forma idempotente en cada arranque.

Turso (libSQL)

Turso es la base de datos en producción. Es SQLite servido sobre el wire de libSQL, accesible desde cualquier región. Para RecUp encaja bien porque:

  • Bajo volumen por usuario (decenas o cientos de incidencias).
  • Consultas sencillas, sin joins complejos ni transacciones largas.
  • Coste muy bajo en el plan free y backups automáticos.
  • Tests con altísima fidelidad gratis. libSQL es un fork de SQLite, así que el mismo SQL y el mismo cliente @libsql/client funcionan tanto contra Turso remoto como contra un SQLite local. En tests basta con cambiar TURSO_DATABASE_URL a :memory: (una BD efímera en RAM que se crea y destruye con el proceso). Resultado: los tests ejercitan el mismo código de producción, los mismos CREATE, INSERT y constraints reales — sin mocks, sin un “DB driver de test” paralelo, y sin riesgo de divergencia entre lo que pasa el test suite y lo que pasa en prod.

Cliente

Se usa el SDK oficial @libsql/client. La instancia es un singleton exportado por server/db.js: 

import { createClient } from '@libsql/client';

const db = createClient({
  url: config.tursoUrl,        // libsql://… o file: o :memory:
  authToken: config.tursoAuthToken || undefined,
});

export default db;

Variables de entorno

VarObligatoriaNotas
TURSO_DATABASE_URL Sí URL del libSQL remoto (libsql://…) en producción, o :memory: en tests. Validado al arrancar.
TURSO_AUTH_TOKEN Sí en prod Token de acceso al libSQL remoto. Se omite con :memory:.
CRYPTO_SECRET Sí Secreto base para derivar la clave AES-256-GCM que cifra las API keys de ClickUp, Anthropic y OpenAI almacenadas en users.
CRYPTO_SECRET no se rota

Si pierdes o cambias CRYPTO_SECRET, las columnas cifradas existentes quedan irrecuperables (no hay re-encrypt automático con clave anterior). Genérala una vez con openssl rand -base64 32 y guárdala en el password manager del equipo.

Inicialización y migraciones

initDb() es la función arrancada al importar server/db.js. Aplica el esquema base con CREATE TABLE IF NOT EXISTS y añade columnas nuevas con ALTER TABLE … ADD COLUMN envuelto en try/catch para tolerar el error si la columna ya existe. 

try { await db.execute('ALTER TABLE users ADD COLUMN avatar_url TEXT'); } catch {}
try { await db.execute('ALTER TABLE users ADD COLUMN anthropic_api_key TEXT'); } catch {}
// …
Migraciones idempotentes, no versionadas

No hay un sistema de migraciones tipo Knex o Prisma Migrate. Cada cambio de esquema se añade como otro CREATE IF NOT EXISTS o ALTER … ADD COLUMN envuelto en try/catch. Funciona porque el equipo es pequeño y los cambios son aditivos. Si el esquema empieza a requerir renombrados, drops o backfills coordinados, conviene introducir un runner real.

Tabla incidents

Una incidencia por bug capturado (voz, texto o extensión).

CREATE TABLE IF NOT EXISTS incidents (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  user_id INTEGER NOT NULL REFERENCES users(id),
  transcript TEXT,
  title TEXT,
  bullets TEXT,                -- JSON.stringify(string[])
  status TEXT DEFAULT 'procesando'
    CHECK(status IN ('procesando','completado','error')),
  source_type TEXT
    CHECK(source_type IN ('audio','text','extension')),
  duration_ms INTEGER DEFAULT 0,
  clickup_task_id TEXT,
  clickup_task_url TEXT,
  created_at TEXT DEFAULT (datetime('now'))
);

CREATE INDEX IF NOT EXISTS idx_incidents_user_id ON incidents(user_id);
ColumnaTipoDescripción
idINTEGER PKAutoincrement.
user_idINTEGER FKDueño de la incidencia (users.id). Verificado por assertOwnership.
transcriptTEXTTexto crudo (transcripción del audio o input del usuario).
titleTEXTTítulo corto generado por la IA tras summarize.
bulletsTEXTArray de bullets serializado como JSON. Se parsea en IncidentService.parseBullets.
statusTEXTprocesando al crear · completado tras summarize · error si falla. Enforced por CHECK.
source_typeTEXTaudio · text · extension. Enforced por CHECK.
duration_msINTEGERDuración del audio en ms. 0 para fuentes text/extension.

created_atTEXTUsado para ordenar el feed (DESC).
Por qué bullets como TEXT (JSON) y no tabla aparte

Los bullets siempre se leen y escriben en conjunto, nunca se consultan por su contenido. Modelarlo como tabla separada añadiría joins sin aportar nada. Es un trade-off consciente a favor de la simplicidad.

Cifrado de columnas sensibles

Las API keys (clickup_api_key, anthropic_api_key, openai_api_key) se cifran antes de persistir con AES-256-GCM. La clave deriva de CRYPTO_SECRET vía SHA-256.

Formato del valor almacenado

enc:v1:<base64( iv ‖ ciphertext ‖ tag )>
  • enc:v1: — prefijo para detectar valores ya cifrados (versionado por si cambia el algoritmo).
  • iv — 12 bytes aleatorios por valor (nonce GCM).
  • ciphertext — texto cifrado.
  • tag — 16 bytes de auth tag GCM (detecta manipulación).

Flujo en código

  • encrypt(plain) y decrypt(value) en server/services/crypto.js.
  • En el endpoint PUT /api/settings se cifra antes del UPDATE.
  • getUserSettings(userId) en db.js descifra al leer, así el resto del backend trabaja con texto plano sin enterarse del cifrado.
  • GET /api/settings nunca devuelve la clave en claro: sólo { configured, hint } (hint = enmascarado con 4 últimos chars).

Migración suave de claves en claro

Contexto. Antes de introducir el cifrado, las columnas clickup_api_key, anthropic_api_key y openai_api_key se guardaban en texto plano. Al activar el cifrado quedaron filas mixtas: las nuevas ya se escriben con el prefijo enc:v1:, pero las viejas seguían en claro. Hacían falta dos cosas: (1) que el código de lectura tolerase ambos formatos, y (2) que los datos antiguos acabaran cifrados sin requerir un script manual ni una ventana de mantenimiento.

Qué hace migrateEncryptApiKeys(). Se ejecuta una vez por arranque del servidor (la llama initDb()). Recorre todas las filas de users, mira cada columna cifrable, y para cada valor que no empiece por enc:v1: ejecuta encrypt() y reescribe la fila. Los valores ya cifrados se ignoran (la función isEncrypted() los detecta por prefijo). Los nulos también se saltan.

Por qué este enfoque.

  • Sin downtime ni coordinación. No requiere apagar el servicio, ejecutar un script SQL externo y volver a levantar: con desplegar la versión que cifra, el siguiente boot deja la BD coherente.
  • Idempotente. En el segundo arranque ya no queda nada en claro, así que la migración es un no-op. Es seguro dejarla siempre activa.
  • Auto-cura. Si en algún momento se restaurase un backup viejo o se insertara una clave en claro por error, el próximo reinicio la cifraría automáticamente.
Cuándo dejará de tener sentido

Una vez confirmado que no quedan filas con prefijo distinto a enc:v1: en producción, esta migración se puede eliminar para evitar un scan completo de users en cada boot. Mientras la tabla sea pequeña, el coste es irrelevante y la red de seguridad compensa.

Base de datos en tests

Los tests no pegan a Turso. El preload de Bun en tests/preload.js fija TURSO_DATABASE_URL=:memory: antes de cargar db.js. Como libSQL acepta el mismo URL que SQLite, todo el código de prod corre tal cual contra una BD en memoria efímera por test run.

Operación

Backups

Hay dos capas de backup, complementarias:

  1. Point-in-time recovery de Turso. Gestionado por el proveedor. La ventana de retención depende del plan: 1 día en Free, 10 d en Developer, 30 d en Scaler, 90 d en Pro. RecUp está en Free, así que PITR cubre incidentes detectados en las últimas 24 h y poco más.
  2. Dumps semanales en GitHub Releases. Copia portátil fuera de Turso. Es la única red de seguridad real a medio/largo plazo mientras estemos en Free: si un borrado o corrupción aparece pasadas 48 h, el PITR de Turso ya no llega y se restaura desde la release semanal más cercana (≈ 12 semanas de historial, una por release).

Cómo funcionan los dumps semanales

  • Workflow: .github/workflows/turso-backup.yml. Cron 0 4 * * 1 (lunes 04:00 UTC) + disparo manual desde Actions → Turso Backup → Run workflow.
  • Script: scripts/backup-turso.sh. Llama al endpoint /dump de Turso con el TURSO_AUTH_TOKEN, descarga el SQL, lo carga en una SQLite temporal para verificar que las tablas users e incidents están presentes, y comprime con gzip -9.
  • Publicación: el .sql.gz se sube como asset de una GitHub Release con tag backup-YYYY-MM-DD-HHMM. No se commitea al repo: vive en Releases.
  • Rotación: el propio job borra todas las releases con prefijo backup- salvo las 12 más recientes.
  • Secrets en el repo (Settings → Secrets → Actions): TURSO_DATABASE_URL y TURSO_AUTH_TOKEN. El upload usa el GITHUB_TOKEN built-in.
  • Doc operativa completa (restore manual, probar el script en local, disparo manual desde CLI): scripts/BACKUP.md.
Backups y CRYPTO_SECRET

Los dumps contienen las columnas sensibles tal cual están en BD, es decir cifradas. Restaurarlos y volver a usar las API keys requiere el mismo CRYPTO_SECRET que tenía el servidor cuando se cifraron. Si se pierde el secret, el restore sigue sirviendo para usuarios e incidencias pero las API keys hay que reintroducirlas a mano. Guarda CRYPTO_SECRET al menos en: env de Render, .env local y un password manager.

CLI de Turso

  • turso db shell <db> — inspeccionar prod.
  • turso db tokens create <db> — emitir/rotar TURSO_AUTH_TOKEN.
  • turso db create <name> --from-file dump.sql — crear una BD nueva desde un dump (útil para restore desde un backup de Releases).
