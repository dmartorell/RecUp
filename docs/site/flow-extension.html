Flujos

Chrome Extension ↔ Webapp

La extensión abre el webapp y transfiere la sesión sin pedirle al usuario un segundo login. Funciona mediante query params cuando la pestaña no existe, y mediante postMessage cuando ya está abierta. El logout se propaga en sentido contrario.

Visión general

[Chrome Extension]
  ├── popup.js        — login propio, graba audio, envía incidents, abre webapp
  ├── background.js   — service worker: context menu "Enviar a RecUp"
  ├── content.js      — relay de mensajes window ↔ runtime
  └── config.js       — RECUP_URL (prod/local)

        │
        │  Hay dos canales de comunicación según el estado de la pestaña:
        │
        ├── Tab nueva       → query params en la URL  (?token=…&email=…&contextText=…)
        │                       └── adoptExtensionSession() + handleExternalText()
        │
        └── Tab existente   → chrome.scripting.executeScript → window.postMessage
                                └── handlePostMessage() en el webapp

Componentes de la extensión

Manifest V3

El fichero chrome-extension/manifest.json declara:

  • Permisos: storage, tabs, contextMenus, scripting.
  • Host permissions: https://recup.onrender.com/* y http://localhost:3000/*. Son necesarios para inyectar scripts con chrome.scripting.executeScript.
  • Service worker: background.js — gestiona el menú contextual y escucha mensajes de logout.
  • Content script: content.js — inyectado en las páginas de RecUp, hace de relay entre el contexto de la página (window) y el service worker (chrome.runtime).

Almacenamiento de sesión en la extensión

La extensión guarda la sesión en chrome.storage.local con tres claves: recup_token, recup_email y recup_name. Este almacenamiento persiste entre reinicios del navegador y es independiente del localStorage del webapp.

Al arrancar el popup (chrome-extension/popup.js:444), recupera estas claves: si existen, muestra la interfaz idle y valida el token contra GET /api/incidents?limit=1. Si el servidor devuelve 401, limpia el storage y muestra el login.

Flujo A: menú contextual → tab nueva

Este es el flujo que se activa cuando el usuario selecciona texto en cualquier página, hace clic derecho y elige "Enviar a RecUp", y no hay ninguna pestaña de RecUp abierta. 

[background.js — contextMenus.onClicked]
  1. Lee chrome.storage.local → { recup_token, recup_email, recup_name }
  2. Comprueba si hay tabs con URL = RECUP_URL/* → ninguna
  3. Construye URL:
       RECUP_URL/?contextText=<encoded>&token=<token>&email=<email>&name=<name>
  4. chrome.tabs.create({ url })

[Webapp — DOMContentLoaded en src/js/app.js:688]
  1. adoptExtensionSession()   — lee ?token, ?email, ?name y los persiste en localStorage
  2. checkAuth()               — ya hay sesión → muestra la app
  3. loadIncidents()
  4. handleExternalText()      — lee ?contextText → createIncident(contextText)
  5. history.replaceState()    — limpia todos los query params de la URL
Por qué limpiar la URL

El JWT viaja en la URL solo el tiempo necesario. history.replaceState() lo elimina antes de que el usuario pueda copiarlo, compartirlo o que quede en el historial del navegador. La sesión ya está en localStorage en ese punto.

Flujo B: menú contextual → tab existente

Si ya hay una pestaña de RecUp abierta, el background no puede modificar su URL sin interrumpir al usuario. En su lugar, usa inyección de script para enviar un mensaje directo al contexto de la página. 

[background.js — contextMenus.onClicked]
  1. chrome.tabs.query({ url: RECUP_URL/* }) → hay una tab
  2. Llama a injectPostMessage(tabId, {
       type: 'recup:extension-data',
       contextText, token, email, name
     })
  3. chrome.scripting.executeScript ejecuta window.postMessage(msg, '*') en la tab
  4. Si falla (tab aún cargando), reintenta hasta 5 veces con 400 ms de delay
  5. chrome.tabs.update(tabId, { active: true }) — pone la tab en foco

[Webapp — handlePostMessage en src/js/app.js:609]
  1. Verifica event.origin === window.location.origin
  2. Si lleva token + email y no hay sesión activa:
       - Guarda la sesión en localStorage
       - showApp(email) + loadIncidents()
  3. Si ya hay sesión:
       - createIncident(contextText)  (si viene contextText)
  4. history.replaceState() no es necesario: la URL no cambió

Flujo C: incident enviado desde el popup

El popup tiene su propia interfaz de grabación/texto. Cuando el usuario envía un incident desde el popup: 

[popup.js — sendBtn click]
  1. POST /api/incidents  con Authorization: Bearer <recup_token>
  2. Obtiene incidentId del response
  3. Si hay tab de RecUp abierta:
       injectPostMessage(tabId, { type: 'recup:extension-data',
                                  token, email, name,
                                  highlight: incidentId })
  4. Si no hay tab:
       chrome.tabs.create({ url: RECUP_URL/ })
       (el webapp cargará y renderizará el incident vía loadIncidents)
  5. window.close()  — cierra el popup

[Webapp — handlePostMessage]
  Si hay highlight → highlightTarget(incidentId)
    → scrollIntoView + añade clase 'incident-highlight' 3 s
    → si el incident ya tiene summary y no tiene ticket → abre modal de ClickUp

Sincronización del token

El popup intercepta la cabecera X-New-Token en cada respuesta de la API (popup.js:9), igual que el webapp. Cuando el servidor renueva el JWT de forma silenciosa, ambos lados lo actualizan en su almacenamiento respectivo:

  • Webapp: actualiza localStorage['recup_session'].token.
  • Popup: actualiza chrome.storage.local['recup_token'].

Esto garantiza que el popup y el webapp nunca tengan tokens distintos aunque uno renueve antes que el otro: el último que hace una request gana.

Logout: de webapp a extensión

Cuando el usuario hace logout en el webapp (o la sesión expira por 401), el flujo se propaga a la extensión a través de content.js: 

[src/js/app.js:250]
  window.postMessage({ type: 'recup:logout' }, '*')

[chrome-extension/content.js:1]
  window.addEventListener('message') → relay a chrome.runtime.sendMessage

[chrome-extension/background.js:23]
  chrome.runtime.onMessage → chrome.storage.local.remove(['recup_token', 'recup_email', 'recup_name'])

El content script es necesario porque el service worker no tiene acceso a window de la página. Actúa de puente entre el contexto de la página y el service worker.

Consideraciones de seguridad

  • Origin check en postMessage — handlePostMessage verifica event.origin === window.location.origin (src/js/app.js:610) antes de procesar cualquier mensaje. Sin este check, cualquier página podría inyectar una sesión falsa.
  • Token en query params — solo viaja en la URL cuando no hay tab existente. history.replaceState lo elimina inmediatamente al arrancar. No persiste en el historial del navegador.
  • chrome.storage.local vs localStorage — el token de la extensión vive en chrome.storage.local, aislado del localStorage de la página. Un XSS en el webapp no puede leer el storage de la extensión.
  • host_permissions — la extensión solo puede inyectar scripts en recup.onrender.com y localhost:3000. No tiene acceso a ningún otro origen.
