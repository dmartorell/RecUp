Creación de ticket ClickUp

Cómo el usuario convierte un bug report en un ticket de ClickUp: el modal del frontend recopila los metadatos, el backend resuelve el email del reporter a un userId (con caché de 10 min), crea la tarea con custom fields y sube los adjuntos.

Visión general

[Frontend: openTicketModal({ title, bullets, transcript })]
        │  Usuario elige: app, plataforma, versión, assetId, adjuntos
        │  POST /api/ticket { name, markdown_description, reporterEmail,
        │                     assetId, platform, product, appVersion }
        ▼
[server/routes/ticket.js]
  ├── Valida name (string no vacío)
  ├── getUserSettings(userId)    ← descifra clickup_api_key + lee clickup_list_id
  ├── Construye markdown_description
  ├── Construye custom_fields (assetId, plataforma, versión)
  ├── resolveEmailToUserId(reporterEmail, apiKey)
  │     └── getWorkspaceMembers → GET /v2/team  (caché in-memory 10 min)
  ├── createTask → POST /v2/list/{listId}/task   (priority: 3)
  └── setReporterField(taskId, userId, apiKey)
        │
        ▼
{ id, url }
        │  Si hay adjuntos: POST /api/attachment  multipart (taskId + files)
        ▼
[server/routes/attachment.js]
  └── Para cada archivo: uploadAttachment → POST /v2/task/{id}/attachment
        │
        ▼
Toast con link al ticket en ClickUp

Modal del frontend

Se abre con openTicketModal(incidentData) (src/js/ticket-modal.js:140). Pre-rellena automáticamente:

  • Título — incidentData.title (el generado por la IA)
  • Descripción — bullets del summary, uno por línea con -
  • App seleccionada por defecto: alfred / plataforma: iOS

El usuario puede cambiar o completar:

  • App — badges: alfred, nn, lavidda, dkey, assets, assets-beta
  • Plataforma — iOS, Android, Web (multiseleción excepto Web)
  • Versión de la app — texto libre
  • Asset ID / Proyecto — texto libre
  • Adjuntos — hasta 5 archivos, máx. 100 MB por archivo, o foto con cámara

Validación en dos pasos

Si el usuario pulsa "Crear ticket" con campos opcionales vacíos (versión, assetId), el primer click muestra un banner con la lista de campos que faltan y no envía. El segundo click envía aunque los campos sigan vacíos. Esto evita bloquear al usuario cuando los campos realmente no aplican.

El único campo obligatorio que bloquea siempre es el título: si está vacío, aparece un error en el modal y no se avanza.

Construcción del payload

El frontend construye markdown_description antes de enviar (src/js/ticket-modal.js:324): 

**Resumen de la incidencia:**

- Bullet 1.
- Bullet 2.

---

**Transcripción completa:**

<transcripción original>

---
**Producto:** Alfred
**ID de Asset o Proyecto:** <assetId>
**Plataforma:** iOS
**Versión:** Alfred 3.2.1

El backend añade el bloque de metadatos al final del description (server/routes/ticket.js:24). Los custom fields de ClickUp reciben esos mismos datos de forma estructurada (ver sección siguiente).

Resolución email → userId (caché 10 min)

ClickUp requiere el userId numérico para asignar el campo "Reporter". El email del usuario logueado está disponible en la sesión (getSession().user.email), pero la API de ClickUp no acepta email directamente.

ClickUpService.resolveEmailToUserId(email, apiKey) (server/services/ClickUpService.js:34) hace:

  1. Llama a getWorkspaceMembers(apiKey), que consulta GET /v2/team.
  2. El resultado se guarda en un Map en memoria (membersCache) con timestamp. Si una petición posterior llega antes de 10 minutos (CLICKUP_CACHE_TTL = 10 * 60 * 1000), devuelve el caché sin volver a llamar a ClickUp.
  3. Busca el miembro cuyo email coincida (comparación en minúsculas) y devuelve su id.

Si el email no está en el workspace, resolveEmailToUserId devuelve null y el endpoint responde 403 NO_MEMBER. El frontend cierra el modal y muestra un toast; no intenta crear la tarea.

Caché in-memory y escalabilidad

Con múltiples instancias del servidor, cada una tiene su propio caché. Una rotación de API key o un nuevo miembro puede tardar hasta 10 min en reflejarse. En un entorno multi-instancia haría falta Redis. Ver Escalabilidad — caché ClickUp.

Creación de la tarea

ClickUpService.createTask (server/services/ClickUpService.js:52) llama a POST /api/v2/list/{listId}/task con:

  • name — título del bug
  • markdown_description — descripción completa construida por el frontend
  • priority: 3 — normal (escala ClickUp: 1 urgente, 2 alta, 3 normal, 4 baja)
  • custom_fields — array con los campos estructurados (ver tabla abajo)

Una vez creada, setReporterField(taskId, userId, apiKey) hace una segunda llamada para asignar el campo "Reporter" (campo tipo People): 

POST /api/v2/task/{taskId}/field/{CLICKUP_CUSTOM_FIELD_IDS.reporter}
{ "value": { "add": [userId] } }

Custom fields

Campo ID ClickUp Fuente en RecUp Cómo se envía
Reporter c9fb2e87-… Email del usuario logueado → resolución a userId setReporterField (llamada separada)
Asset ID / Proyecto 3aedd038-… Input ticket-asset-id custom_fields en createTask
Dispositivo / Plataforma b07abf0c-… Badges de plataforma (iOS, Android, Web…) custom_fields en createTask
Versión de la app 66097442-… product + appVersion concatenados custom_fields en createTask
Captura 567894b1-… Archivos adjuntos uploadAttachment con ?custom_field_id=

Los IDs viven en CLICKUP_CUSTOM_FIELD_IDS (server/config/constants.js:2) y son específicos del workspace.

Subida de adjuntos

Una vez el backend devuelve { id, url } con el taskId, el frontend sube los adjuntos en una segunda petición (src/js/ticket-modal.js:245): 

POST /api/attachment
Content-Type: multipart/form-data

taskId=<taskId>
attachment=<file1>
attachment=<file2>
…

El servidor (server/routes/attachment.js) usa multer con almacenamiento en memoria (memoryStorage), límite de 100 MB por archivo y máximo 5 archivos por request. Para cada archivo llama a ClickUpService.uploadAttachment, que hace: 

POST /api/v2/task/{taskId}/attachment?custom_field_id={captura_field_id}
Content-Type: multipart/form-data  (FormData con el Blob del archivo)

El bucle es secuencial: si falla un archivo, la respuesta incluye el error y el array uploaded con los que ya se subieron.

Error parcial y retry

Si la subida de adjuntos falla después de crear la tarea, el frontend:

  1. Marca la tarjeta de incidente como enviada (la tarea ya existe en ClickUp).
  2. Muestra un error en el modal con un botón Reintentar adjuntos.
  3. El retry vuelve a llamar a /api/attachment con todos los archivos pendientes.
  4. Si el retry también falla, el modal queda abierto con el botón disponible de nuevo.

El usuario no pierde el ticket aunque los adjuntos fallen — la tarea en ClickUp ya está creada.

Errores posibles

Código HTTP Error Causa
400 NAME_REQUIRED El campo name está vacío o ausente
400 SETTINGS_NOT_CONFIGURED El usuario no tiene clickup_api_key o clickup_list_id
401 — JWT inválido (devuelto por authMiddleware)
403 NO_MEMBER El email del usuario no pertenece al workspace de ClickUp
4xx/5xx CLICKUP_API_ERROR La API de ClickUp devolvió error al crear la tarea
4xx/5xx CLICKUP_UPLOAD_ERROR Fallo al subir un adjunto; incluye uploaded con los exitosos
400 TASK_ID_REQUIRED taskId ausente en POST /api/attachment
400 FILE_REQUIRED No se adjuntó ningún archivo en POST /api/attachment
