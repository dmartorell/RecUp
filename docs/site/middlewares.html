Backend · Pipeline

Middlewares

Cómo es el viaje de un request en RecUp desde que entra hasta que se responde: orden global del pipeline en server/app.js, middlewares propios (auth, rate limit, error handler) y los de terceros que se montan en él (express.json, Sentry, multer).

El pipeline de un request

Todo está cableado en server/app.js. Este es el orden literal en el que se ejecutan los middlewares globales: 

const app = express();

app.set('trust proxy', 1);              // 1. confianza en proxy (Render)
app.use(express.json());                // 2. body parser JSON

app.use(authRouter);                    // 3. routers
app.use(summarizeRouter);
app.use(ticketRouter);
app.use(attachmentRouter);
app.use('/api/incidents', incidentsRouter);
app.use(settingsRouter);

Sentry.setupExpressErrorHandler(app);   // 4. handler de errores de Sentry
app.use(errorHandler);                  // 5. handler de errores propio

Qué hace cada paso

#PasoPara qué
1 trust proxy: 1 Indica a Express que confíe en el primer proxy delante (Render). Sin esto, req.ip sería la IP del proxy y el rate limiter contaría a todos los usuarios como uno solo.
2 express.json() Parsea bodies application/json y deja el objeto en req.body. Las rutas que reciben multipart (attachments) usan multer en su lugar.
3 Routers Cada router se monta global o bajo prefijo. Dentro, las rutas individuales aplican middlewares por ruta: rateLimit en register/login, authMiddleware en todo lo demás.
4 Sentry.setupExpressErrorHandler Captura el error y lo envía a Sentry. Va antes del handler propio porque si éste respondiera primero, Sentry nunca lo vería.
5 errorHandler Serializa el error como { success, error }, mapea status y hace logging. Es el último paso antes del cliente.
Resumen mental

trust proxy → JSON body → router (rateLimit/auth si aplica → handler) → si error: Sentry → respuesta JSON. Mantener este orden literal en app.js es lo que garantiza que el rate limiter ve la IP correcta, que los handlers reciben req.body ya parseado y que los errores se capturan y formatean.

Middlewares propios

authMiddleware

Protege todas las rutas privadas. Verifica el JWT, escribe req.user y renueva el token silenciosamente vía cabecera X-New-Token si está cerca de caducar.

Detalles completos (payload, TTL, política de renovación, storage por cliente y handoff con la extensión): ver Token y JWT. Aquí solo aparece para situarlo en el pipeline.

  • Fichero: server/middleware/auth.js.
  • Se aplica por ruta, no globalmente — las rutas públicas no lo llevan.
  • Errores que produce: 401 UNAUTHORIZED.

rateLimiter

Limitador en memoria, por IP, con ventana deslizante. Diseñado para frenar fuerza bruta sobre las rutas públicas de auth. Vive en server/middleware/rateLimiter.js. 

export function createRateLimiter({
  windowMs = RATE_LIMIT_WINDOW_MS,   // 60_000 ms
  max      = RATE_LIMIT_MAX,         // 10 requests
} = {}) {
  const attempts = new Map();          // ip → timestamps[]
  return (req, res, next) => {
    const key = req.ip;
    const now = Date.now();
    const recent = (attempts.get(key) || []).filter(t => now - t < windowMs);
    if (recent.length >= max) {
      return res.status(429).json({ success: false, error: 'RATE_LIMITED' });
    }
    recent.push(now);
    attempts.set(key, recent);
    next();
  };
}

Cómo funciona

  • Por cada request guarda el timestamp en un array asociado a req.ip.
  • En la siguiente request descarta del array los timestamps de hace más de windowMs (60 s). Si quedan ≥ max (10), responde 429 RATE_LIMITED.
  • Ventana deslizante, no fija: a las 10 req no se desbloquea a los 60 s exactos, sino a medida que cada timestamp envejece.

Dónde se aplica

En server/routes/auth.js: 

const rateLimit = createRateLimiter();

router.post('/api/auth/register', rateLimit, …);
router.post('/api/auth/login',    rateLimit, …);

Importante: las dos rutas comparten el mismo attempts (la closure se crea una sola vez). Así, 10 intentos por IP cubren register + login combinados — no son 10 + 10. Es lo que queremos: un atacante no puede alternar las dos rutas para duplicar su presupuesto.

Limitaciones conscientes
  • In-memory: si hay varias instancias del backend, cada una tiene su propio contador. Hoy RecUp corre en una sola instancia en Render, así que no es un problema. Si en algún momento escalas horizontalmente, esto deja de ser efectivo y hay que mover el contador a Redis.
  • Por IP, no por cuenta: alguien detrás de un NAT (oficina, VPN compartida) puede agotar el límite con tráfico legítimo. El umbral de 10/min está pensado para tolerar ese caso.
  • Sin barrido: el Map nunca se purga; las IPs inactivas conservan su array hasta que se reinicia el proceso. En volúmenes actuales el coste de memoria es negligible.

errorHandler

Último middleware del pipeline. Convierte cualquier excepción que llegue por next(err) en una respuesta JSON con el mismo contrato que el resto de endpoints. Vive en server/middleware/errorHandler.js. 

export function errorHandler(err, req, res, _next) {
  const rawStatus = err.status || 500;
  const status    = rawStatus === 401 ? 502 : rawStatus;
  const code      = err.code || 'INTERNAL_ERROR';
  if (status >= 500) console.error(`[ERROR] ${req.method} ${req.path}:`, err.message);
  return res.status(status).json({ success: false, error: code });
}

Contrato de salida

{ "success": false, "error": "INTERNAL_ERROR" }

Mismo envoltorio que el resto de respuestas de error de la API. El cliente solo tiene que mirar success y mapear error a un string i18n.

Por qué 401 → 502

Si un servicio aguas abajo (ClickUp, Anthropic, OpenAI) responde 401 a una llamada del backend, eso significa fallo de auth del backend con el proveedor, no del usuario con RecUp. Reenviar el 401 tal cual al cliente dispararía el flujo de "sesión caducada" (logout + reload) por una causa que no es la suya: ver interceptor del SaaS. Reescribirlo como 502 BAD_GATEWAY mantiene la semántica correcta: "tu sesión está bien, pero un proveedor falló".

Logging

Solo se loguea por console.error cuando el status es ≥ 500. Los errores 4xx son ruido (clientes mandando peticiones malformadas), así que se ignoran. Sentry recibe el evento aparte vía el handler que va justo antes.

Middlewares de terceros

express.json()

  • Parsea bodies application/json y los deja en req.body.
  • No aplica a POST /api/attachment: ese endpoint es multipart y lo maneja multer.
  • Si el body no es JSON válido, el propio middleware llama a next(err) con status 400, que termina en errorHandler.

Sentry.setupExpressErrorHandler

Captura el error en Sentry y lo pasa al siguiente handler. No responde al cliente; solo observa. Por eso va antes de errorHandler.

Política, PII, environments, filtros de ruido: ver Sentry.

multer (en /api/attachment)

Único endpoint multipart. Multer se monta por ruta, no globalmente: 

const upload = multer({
  storage: multer.memoryStorage(),
  limits: { fileSize: MULTER_MAX_FILE_SIZE },   // 100 MB
});

router.post(
  '/api/attachment',
  authMiddleware,
  upload.array('attachment', MULTER_MAX_FILES), // máx 5 ficheros
  handler,
);
  • Memory storage: los ficheros nunca se escriben en disco del backend; se procesan en RAM y se reenvían a ClickUp. Esto evita acumulación de basura en el filesystem y simplifica el lifecycle.
  • Límites declarados como constantes en server/config/constants.js (MULTER_MAX_FILE_SIZE y MULTER_MAX_FILES). Tocar el tamaño máx se hace en un único sitio.
  • Detalle del endpoint: POST /api/attachment.
