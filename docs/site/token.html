Auth · Sesiones

Token y JWT

RecUp usa un único JWT como prueba de identidad. Lo emite el backend al registrarse o hacer login, viaja en cada request como cabecera Authorization, y se renueva de forma silenciosa antes de que caduque. La app web y la extensión de Chrome comparten el mismo token, con almacenamiento distinto.

Qué es el JWT

Un JSON Web Token firmado por el backend con JWT_SECRET. La librería es jsonwebtoken y se firma con el default (HS256, simétrico). El payload es mínimo: 

{
  "sub": 42,                       // users.id
  "name": "Dani",
  "email": "dani@empresa.com",
  "iat": 1717977600,               // emitido (epoch s)
  "exp": 1718582400                // expira (epoch s)
}

El payload no está cifrado, solo firmado: cualquiera puede decodificarlo (es base64). Lo que protege la firma es que si manipulas un campo, la verificación con JWT_SECRET falla en el backend.

No metas datos sensibles en el payload

El token viaja a cliente y se queda almacenado en su disco. name y email ya son los datos que el cliente conoce de sí mismo. No añadir password, API keys, ni claims internos.

Emisión

signToken(userId, name, email) en server/middleware/auth.js es el único punto que emite tokens. Lo invocan:

  • POST /api/auth/register — en la respuesta de creación de cuenta.
  • POST /api/auth/login — tras validar credenciales con bcrypt.
  • El propio authMiddleware — al renovar silenciosamente (ver Renovación). 
export function signToken(userId, name, email) {
  return jwt.sign(
    { sub: userId, name, email },
    config.jwtSecret,
    { expiresIn: JWT_EXPIRES_IN }   // '7d'
  );
}

Caducidad

ConstanteValorSignificado
JWT_EXPIRES_IN '7d' El token expira a los 7 días desde su emisión. La librería rellena exp y iat automáticamente.
JWT_RENEW_THRESHOLD_MS 3 días (en ms) Umbral a partir del cual el backend devuelve un token nuevo en la respuesta. Ver renovación.

Ambos viven en server/config/constants.js — un único sitio para tocar la política de sesiones.

Validación en cada request

authMiddleware protege todas las rutas autenticadas. Espera: 

Authorization: Bearer <jwt>
  1. Si falta la cabecera o no empieza por Bearer → 401 UNAUTHORIZED.
  2. jwt.verify(token, JWT_SECRET) comprueba firma y expiración. Si el token está expirado o la firma es inválida → 401 UNAUTHORIZED.
  3. Si pasa, escribe req.user = { id, name, email } y el handler sigue normal.

Renovación silenciosa

RecUp no usa refresh tokens. En su lugar, authMiddleware renueva en banda: si al validar detecta que al token le quedan menos de JWT_RENEW_THRESHOLD_MS de vida, firma uno nuevo y lo adjunta como cabecera de respuesta: 

const expMs = decoded.exp * 1000;
if (expMs - Date.now() < JWT_RENEW_THRESHOLD_MS) {
  const fresh = signToken(decoded.sub, decoded.name, decoded.email);
  res.setHeader('X-New-Token', fresh);
  res.setHeader('Access-Control-Expose-Headers', 'X-New-Token');
}

El cliente intercepta cada respuesta y, si trae la cabecera, sustituye el token guardado.

Vida efectiva de una sesión activa

Con TTL 7 d y umbral 3 d, mientras el usuario haga al menos una request cada ≤ 4 días nunca verá la sesión expirada: cada vez que entra en esa ventana de "quedan menos de 3 días", la respuesta le trae un token nuevo de 7 d. Solo se cae la sesión si no abre la app durante más de 4 días seguidos (entre la última request y la caducidad real).

Almacenamiento por cliente

App web (SaaS)

Guardado en localStorage bajo la clave recup_session: 

localStorage.setItem('recup_session', JSON.stringify({
  token: '<jwt>',
  user: { name, email, avatar }
}));
  • Accesores en src/js/auth.js: getSession(), updateSessionToken(token), authHeaders().
  • authHeaders() es el helper que cada llamada usa para inyectar Authorization y Content-Type.
  • localStorage persiste entre reinicios del navegador hasta que se limpie explícitamente (logout, expiración detectada, devtools).

Extensión de Chrome

Guardado en chrome.storage.local, separado en tres entradas: 

chrome.storage.local.set({
  recup_token: '<jwt>',
  recup_email: 'dani@empresa.com',
  recup_name: 'Dani'
});
  • La extensión no guarda avatar — solo lo necesita para autenticar y enviar al SaaS.
  • Se lee desde popup.js al abrir el popup y desde background.js al disparar el menú contextual "Enviar a RecUp".
  • chrome.storage.local es por instalación de la extensión, no comparte con cookies del navegador.
Por qué localStorage / chrome.storage y no cookies httpOnly

Cookies httpOnly protegerían el token frente a XSS, pero requerirían arquitectura de cookies + CSRF + dominio compartido. RecUp es una SPA en su propio dominio con superficie XSS reducida (no renderiza HTML de terceros sin escapar). El trade-off de complejidad no compensa todavía.

Interceptor de fetch (ambos clientes)

Tanto el SaaS como la extensión monkeypatchean window.fetch al arrancar para automatizar la renovación. Cada respuesta se inspecciona y, si trae X-New-Token, se actualiza el token guardado. 

// src/js/auth.js (SaaS)
const fresh = res.headers.get('X-New-Token');
if (fresh) updateSessionToken(fresh);

// chrome-extension/popup.js (extensión)
const fresh = res.headers.get('X-New-Token');
if (fresh) chrome.storage.local.set({ recup_token: fresh });

Diferencias prácticas:

  • SaaS: además del refresh, al recibir 401 en una ruta no pública dispara handleExpiredSession() — borra recup_session, muestra toast "sesión caducada", postMessage({ type: 'recup:logout' }) para que la extensión se entere, y recarga la página.
  • Extensión: solo refresca el token; el manejo de 401 lo hace cada llamada por su cuenta (vuelve a la pantalla de login). No tiene página que recargar.

AUTH_PUBLIC_PATHS

Un 401 en /api/auth/login o /api/auth/register significa credenciales incorrectas, no sesión caducada. Para no disparar handleExpiredSession() en esos casos, el interceptor comprueba la URL de la request contra una lista de rutas públicas: 

// src/js/auth.js
const AUTH_PUBLIC_PATHS = ['/api/auth/login', '/api/auth/register'];

Si la URL está en esa lista, el 401 se deja pasar al handler de la llamada original (que mostrará el error de credenciales). Si no está, se trata como sesión expirada y se fuerza el logout.

Handoff extensión ↔ SaaS

La extensión y la SPA comparten el mismo backend y por tanto el mismo JWT, pero cada una mantiene su propia copia del token. Cuando el usuario hace clic derecho → Enviar a RecUp, la extensión necesita "trasplantar" su sesión a la pestaña del SaaS.

Flujo

  1. Service worker (background.js) lee recup_token, recup_email, recup_name de chrome.storage.local.
  2. Comprueba si ya hay una pestaña abierta en el dominio del SaaS (RECUP_URL):
    • Sí: inyecta un postMessage con { type: 'recup:extension-data', token, email, name, contextText } en esa pestaña y la enfoca.
    • No: abre nueva pestaña con los datos como query params (?contextText=…&token=…&email=…&name=…).
  3. En el SaaS, adoptExtensionSession() (URL) y handlePostMessage() (postMessage) en src/js/app.js:
    • Solo adoptan la sesión si aún no hay sesión propia (!getSession()?.token). Esto evita pisar un usuario logado con otro.
    • Guardan { token, user: { email, name } } en localStorage.
    • Limpian la URL con history.replaceState para que el token deje de aparecer en location.search y no se filtre a Sentry, referer headers o screenshots.
Token en query params: por qué se acepta y por qué se limpia

Pasar el JWT en la URL no es ideal: puede acabar en el history del navegador, en logs del servidor y en cabeceras Referer. Se acepta como último recurso cuando no hay una pestaña del SaaS abierta donde inyectar el postMessage. Por eso, en cuanto el SaaS arranca, lo primero que hace es borrar los params de la URL con history.replaceState. El token vive en location.search milisegundos.

Logout coordinado

Como hay dos copias del token (una por cliente), un logout en uno debe propagar al otro. Flujo:

  1. SaaS detecta logout (manual o expiración) → emite postMessage({ type: 'recup:logout' }).
  2. El service worker de la extensión escucha chrome.runtime.onMessage y, al recibir recup:logout, borra recup_token, recup_email y recup_name de chrome.storage.local.
  3. En la dirección contraria (logout iniciado en la extensión) solo se limpia el storage local de la propia extensión; el SaaS lo notará la próxima vez que necesite el token (o vía la próxima respuesta 401).
