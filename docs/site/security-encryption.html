Seguridad

Cifrado de API keys en reposo

Cada usuario puede guardar sus propias claves de Anthropic, OpenAI y ClickUp. Estas claves se cifran con AES-256-GCM antes de tocar la base de datos. Si alguien vuelca Turso, obtiene texto cifrado inútil sin CRYPTO_SECRET.

Qué se cifra

Tres columnas de la tabla users:

  • anthropic_api_key
  • openai_api_key
  • clickup_api_key

Lo que no está cifrado con este sistema (y por qué):

  • password — usa bcrypt (hash unidireccional). No necesita reversibilidad.
  • El JWT — se firma con JWT_SECRET pero no se almacena en BD.
  • clickup_list_id — identificador no sensible, no es una credencial.

Cómo funciona AES-256-GCM

AES-256-GCM es cifrado simétrico autenticado. «Autenticado» significa que, además de cifrar, produce un authentication tag de 16 bytes que verifica la integridad. Si alguien modifica el ciphertext en BD, el descifrado lanza un error en lugar de devolver basura silenciosa.

La clave de cifrado es de 32 bytes (256 bits). Se deriva del CRYPTO_SECRET pasándolo por SHA-256: 

// server/services/crypto.js:12
cachedKey = createHash('sha256').update(config.cryptoSecret, 'utf8').digest();

Esto permite que CRYPTO_SECRET sea cualquier string arbitrario (una frase, un base64 de 32 bytes…) y siempre producirá una clave de exactamente 256 bits. La clave derivada se cachea en memoria para no recalcularla en cada operación.

Formato en BD

Cada valor cifrado sigue este layout binario, codificado en base64 con prefijo:

enc:v1:<base64( IV[12 bytes] | ciphertext | authTag[16 bytes] )>

Ejemplo real en Turso:

enc:v1:aGVsbG8gd29ybGQhISEAAAAAAAAAAAABAgMEBQYHCA==
  • Prefijo enc:v1: — marca el valor como cifrado e identifica la versión del esquema.
  • IV (12 bytes) — vector de inicialización aleatorio generado con randomBytes(12) en cada cifrado. Garantiza que cifrar la misma key dos veces produce ciphertexts distintos.
  • Ciphertext — longitud variable, igual a la del plaintext.
  • Auth tag (16 bytes) — producido por GCM para verificar integridad en el descifrado.

Flujo completo: guardar y leer una API key

Guardar (PUT /api/settings)

  1. El usuario envía la clave en claro por HTTPS.
  2. El route handler llama a encrypt(trimmed) (server/routes/settings.js:51).
  3. encrypt genera un IV aleatorio, cifra, concatena IV + ciphertext + tag y devuelve el string con prefijo.
  4. El string cifrado se persiste en Turso. La clave en claro nunca toca el disco.

Leer en el frontend (GET /api/settings)

  1. El backend descifra la columna con decrypt(row[field]).
  2. En lugar de devolver la clave en claro al cliente, pasa el plaintext por hint(plain) que enmascara todo excepto los últimos 4 caracteres: 
// server/services/crypto.js:44
const HINT_MASK = '••••••••••••••••••••••••';
export function hint(value) {
  if (!value) return '';
  const tail = value.slice(-4);
  return `${HINT_MASK}${tail}`;
}

El frontend solo sabe si la clave está configurada y cuáles son sus últimos 4 caracteres. La clave en claro nunca sale del servidor.

Usar en llamadas a IA y ClickUp

  1. getUserSettings(userId) en server/db.js:83 descifra on-demand justo antes de cada request que necesita las keys.
  2. La clave en claro vive solo en memoria durante la duración del request.

Idempotencia de encrypt / decrypt

Ambas funciones son seguras de llamar repetidamente sobre el mismo valor sin efectos secundarios: 

encrypt(null)            // → null
encrypt('')              // → ''
encrypt('enc:v1:...')    // → 'enc:v1:...'  (ya cifrado, lo devuelve tal cual)

decrypt(null)            // → null
decrypt('')              // → ''
decrypt('sk-plaintext')  // → 'sk-plaintext'  (sin prefijo, lo devuelve tal cual)

Esto hace que la migración al arranque sea segura: si una key ya estaba cifrada de una ejecución anterior, encrypt la deja intacta.

Migración automática al arranque

Al iniciar el servidor, initDb() llama a migrateEncryptApiKeys() (server/db.js:63). Esta función recorre todos los usuarios y cifra cualquier columna que aún esté en claro (sin prefijo enc:v1:). Esto cubrió la transición cuando se añadió el cifrado sin necesitar una migración manual de datos.

CRYPTO_SECRET

Cómo generarlo

openssl rand -base64 32

Produce 32 bytes aleatorios en base64 (~44 caracteres). Válido como valor de CRYPTO_SECRET; SHA-256 lo reducirá a exactamente 32 bytes para AES-256.

Dónde vive

Solo en el dashboard de Render como variable de entorno del servicio. No está en .env, no está en el repo, no está en los logs. server/config/env.js lo marca como required(): si falta, el servidor no arranca.

Qué pasa si se pierde

Pérdida irrecuperable de API keys cifradas

Si CRYPTO_SECRET se pierde o rota, todas las API keys almacenadas en BD se vuelven irrecuperables. No hay backdoor ni copia de seguridad de la clave de cifrado.

Consecuencia práctica: los usuarios tendrían que volver a introducir sus API keys.

La contraseña de usuario (bcrypt) no se ve afectada: el login sigue funcionando con normalidad.

Rotar CRYPTO_SECRET

No hay un comando de rotación automática. Si se necesita rotar (por ejemplo, ante sospecha de compromiso del secret), el proceso manual sería:

  1. Descifrar todas las keys con el secret antiguo mientras el servidor aún corre.
  2. Actualizar CRYPTO_SECRET en Render.
  3. Re-cifrar todas las keys con el nuevo secret y escribirlas en BD.

Actualmente no existe este tooling. Si se compromete el secret, lo más rápido es resetear todas las columnas a NULL y pedir a los usuarios que reconfiguren.

Límite del modelo actual

Las transcripciones e incidentes no están cifradas. Un volcado de BD expone el contenido de los bug reports. El vector de ataque es acceso a Turso (credenciales de Turso, no de RecUp), que en prod está protegido por TURSO_AUTH_TOKEN guardado en Render.
